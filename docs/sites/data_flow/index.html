GEECS Data Flow

How devices, the EPICS gateways, the Bluesky scan engine, storage and people connect, and where OSPREY plugs in.

fleet as deployed · 2026-09 · GEECS Plugin Suite docs

One scan, end to end

  1. 1A request enters the queue. An operator submits from the console, or OSPREY calls a GEECS-MCP tool. Both go through the same queue API to the RE Manager, so the engine cannot tell them apart.
  2. 2The engine drives hardware through PVs. Setpoints are written to :SP PVs on the CA gateway, which relays them to the LabVIEW device over the GEECS wire protocol and mirrors the readbacks.
  3. 3Every shot lands in three places. Readings become Bluesky documents in Tiled. The capture daemon pulls images from the PVA gateways into HDF5 stacks. LabVIEW devices keep saving their native per-shot files.
  4. 4The engine owns the scan folder. It alone claims ScanNNN, writes ScanInfo and exports the s-file. Analysis code only ever reads that folder.
  5. 5People read it back. Console scan browser, Data Portal and notebooks share one catalog layer over Tiled and the share. MCP answers "what did scan 12 give" from the same place.
  6. 6Analysis runs itself. LiveWatch sees the new s-file, ScanAnalysis runs the configured analyzers, LogMaker posts the figures to the experiment Google Doc.

Where OSPREY plugs in

  • One door. OSPREY reaches GEECS only through GEECS-MCP, which runs next to the queueserver and validates every request against the same config truth the worker uses.
  • Read freely, write through verbs. Read tools cover scan status, history, results and config listings. Control is limited to submit, stop on scans it owns, and clear queue, each with a request cap and an acknowledge loop.
  • Same standing as the console. MCP is a peer client of the queueserver, never an engine internal. Anything an agent does shows up in the queue like an operator's scan.
  • Two write paths, one rule. Anything with GEECS semantics, a scan or a stop, goes through MCP verbs. A single setpoint can still be written to an `:SP` PV by OSPREY's own EPICS write tool, bounded by a limits database extracted from GEECS device limits, the same way any EPICS client would.

Why EPICS in the middle

  • The gateways make GEECS look like any other IOC. Phoebus, Bluesky, an Archiver Appliance or a future twin all work off the shelf with no bespoke bridge.
  • Scalars are central and cheap. Images stay distributed on the camera servers, served only while someone is subscribed.

What runs where today

A sketch. The Fleet Map is the authoritative table of hosts, ports, health checks and runbooks, and the place drift is reconciled.

Central lab server
192.168.6.14 · Ubuntu · systemd

CA gateway, Tiled, GEECS DB. Interim home of the worker-side services too: queueserver, capture daemon, GEECS-MCP HTTP, Data Portal.

Camera servers
Windows · NSSM service

One PVA image gateway per host, beside the LabVIEW camera devices. Images never transit the central gateway.

Device hosts
Windows · LabVIEW

GEECS devices as always. Nothing installed for this stack; the gateway speaks their existing UDP/TCP protocol.

Data share
NAS · SMB

The scan folder tree. Written by the engine, capture daemon and LabVIEW; read by everyone else.

Operator machines
Windows / macOS / Linux

GEECS-Console, Phoebus, notebooks, a browser for the portal, OSPREY. All clients, nothing runs unattended here.
