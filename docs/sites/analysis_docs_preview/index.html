Analysis docs preview

Three ways to document the analysis recipes, each mocked as the page it would produce. Tab A holds a card for every measure the analysis core supports. Where a measure can run without vendor software, the images, overlays and numbers come from running it through geecs_analysis.run.analyze on a synthetic input, the same code path the portal preview uses.

What it is

One reference card per measure (and later per step and summary). Each opens with a figure showing what the measure computes, then a table of every scalar it writes to the s-file.

What's generated

The figure, parameter table and scalar list. The docs build runs each measure's example recipe, reads parameters from the Pydantic schema, and lists scalars from emitted_scalars().

Who it serves

Anyone asking what x_rms or emittance_proxy means, or which measure to pick. It's the page the editor's "?" links point to.

Gap this exposes. The measures list their scalar names but not what they mean. The "meaning" columns here are text I wrote for this preview. Direction A needs each measure to carry a short definition for every scalar beside emitted_scalars(), so the text is written once, next to the code, and both the docs and the editor read it.

What it is

A few hand-written, task-based pages, e.g. "Measure a beam on a camera". Each follows one shot from raw frame to s-file column, with the portal action and the Python call side by side.

What's generated

The images. Each step's picture is rendered at docs build time by running the recipe up to that step. The prose is hand-written and so can drift.

Who it serves

A new student, or you in six months asking "how do I do this without the portal?"

Measure a beam on a camera

A recipe is an ordered list of processing steps followed by one measure. Each step sees the output of the step before it, so order matters.

  1. Open a shot and start a recipe

    In the portal, open the scan, pick the camera, and click edit configs. The editor opens with that shot as its preview input.

  2. Add steps until the preview looks right

    Subtract the pedestal, crop to the beam, remove hot pixels, zero the noise floor. Preview after each step; nothing is saved or written.

    In the portal

    Steps panel → add step → preview

    In Python
    from geecs_analysis.pipeline import apply_pipeline
frame = apply_pipeline(raw_frame, recipe.steps)

  3. Choose the measure and check the numbers

    Pick beam. The preview overlays the centroid and projections and lists the scalars. What each scalar means →

    In the portal

    Measure → beam → preview

    In Python
    from geecs_analysis.run import analyze
result = analyze(raw_frame, recipe)
result.scalars["x_CoM"]

  4. Run it on the whole scan

    Save the recipe, open the scan's Analysis tab, and run. Choose per_shot or per_bin deliberately: averaging images then measuring is not the same as measuring then averaging.

    In the portal

    Analysis tab → select diagnostic → Run

    In Python (what the Run button calls)
    from scan_analysis.config import create_scan_analyzer
analyzer = create_scan_analyzer(diagnostic)
analyzer.run_analysis(scan_tag)

  5. Read the results

    Scalars land as new columns in analysis/sNNN.txt, prefixed by the recipe's output_name. Figures go under analysis/ScanNNN/. ScanData loads both.

Four or five of these would cover the real workflows: beam on a camera, spectrum on a line, background from a dedicated scan, groups for a standard set, and live optimizer measurements. Each doubles as the "without the portal" notebook, because every portal action appears next to its Python call.

What it is

Help where you're working. Each step, measure and summary choice in the config editor gets a "?" that opens a side panel with the short version and a link to the full card.

What's generated

The panel reuses A's output: the same figure and scalar definitions, packaged with the editor. No second copy to maintain.

Who it serves

The operator mid-edit who wants the answer without leaving the page. It depends on A existing.

Open choices

  • Figures: interactive or static? Hover-to-highlight, as in tab A, needs a small inline script per page. Static images are simpler.
  • Example data: synthetic or a real shot? Synthetic is reproducible in CI and has known true values. A real shot is more convincing but needs a small committed fixture, and is the only option for FROG and HASO.
  • Tab name: "Web Services", "Lab Services" or "Operator Guide"?
  • Old notebooks: rewrite onto the recipe path, or delete in favour of the workflow pages?
